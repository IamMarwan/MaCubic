WEEK 19 · API REFERENCE

Document Workflow API

Submit documents, inspect tool decisions, and retrieve durable execution history.

Submit a task

POST /api/v1/runs with Content-Type: application/json

{
  "filename": "drawing.txt",
  "text": "Document Type: Shop Drawing\nProject: Demo Tower\n...",
  "task": "workflow",
  "instruction": "Focus on revision status."
}

Tasks: workflow, review, classify, summarize, revisions. Supply either text or content_base64. PDF bytes must use content_base64 or a raw upload.

Alternatively POST the raw file bytes to /api/v1/runs?filename=drawing.pdf&task=workflow using application/pdf or application/octet-stream.

Available endpoints

GET  /api/v1/health
GET  /api/v1/tools
POST /api/v1/documents/index
POST /api/v1/runs
GET  /api/v1/runs?limit=25&offset=0
GET  /api/v1/runs/{run_id}
GET  /api/v1/runs/{run_id}/events
GET  /api/v1/samples
GET  /openapi.json

Index earlier documents explicitly using the same upload format at /api/v1/documents/index. Indexing requires project, document number and revision. Running a review does not automatically add the file to the register.

Submission is synchronous. A 201 response means a run was recorded: check its status (completed, failed or halted). A failed run retains its partial results and execution history. Rejected uploads return 400 without creating a run. Saturated submissions return 429.

Use run history while an agent request is in progress to inspect recorded planning and tool events. GET endpoints support inspection; they do not start new runs.
